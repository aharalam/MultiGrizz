# MultiGrizz backend API v1

Base URL during local development: `http://localhost:4000`. This is a separate service from Next.js. All timestamps are ISO strings and identifiers are UUIDs. Names and payload fields use snake_case.

## Authentication and isolation

Frontend signs in through Supabase Auth using its publishable key, then sends `Authorization: Bearer <session.access_token>` on all endpoints except `/health` and `/ready`. Refresh through Supabase Auth when necessary. Backend verifies the token with Supabase; never send the secret/service key to a browser.

Team and party are the same concept. Every member of a team can inspect and manage all its agents, squads, contexts, and runs. Other teams cannot access them. The backend verifies membership before resource access; database RLS provides an additional boundary. Shared access does not mean unauthenticated access.

Success envelope: `{ "data": ... }`. Error envelope: `{ "error": { "code": "FORBIDDEN", "message": "..." } }`; validation errors may also include `fields`. Handle HTTP 400 validation, 401 session, 403 membership/origin, 404 resource, 409 duplicate active run, 429 rate limit, 502 database, and 503 missing schema/queue full. Network or model failures appear in persisted run status.

## Teams and shared agents

| Method | Path | JSON body / result |
| --- | --- | --- |
| GET | `/me` | `data: {id}` |
| GET | `/teams` | Up to 100 teams the user belongs to |
| POST | `/teams` | `{name}` → 201, team with `id,name,invite_code,created_by,created_at` |
| POST | `/teams/join` | `{invite_code}` → joined team; idempotent membership |
| GET | `/teams/:teamId` | Team including its invitation code; members only |
| GET | `/teams/:teamId/members` | Up to 100 `{user_id,joined_at}` rows |
| GET | `/teams/:teamId/agents` | Up to 100 agent records |
| POST | `/teams/:teamId/agents` | `{name,role,instructions}` → 201 agent |
| PATCH | `/teams/:teamId/agents/:agentId` | Any nonempty subset of `{name,role,instructions}` |

Agent record: `{id,team_id,name,role,instructions,created_at}`. Name/role max 100 characters; instructions max 2000. Invitation codes are 32 hex characters; anyone with the code can join, so share them only with intended teammates. No separate administrator role in the initial app.

## Squads

| Method | Path | JSON body / result |
| --- | --- | --- |
| GET | `/teams/:teamId/squads` | Up to 100 squads |
| POST | `/teams/:teamId/squads` | `{name,goal?}` → 201 squad |
| GET | `/teams/:teamId/squads/:squadId` | Squad plus `agents: [{agent_id,position,agents: Agent}]` |
| PATCH | `/teams/:teamId/squads/:squadId` | Any nonempty subset of `{name,goal}` |
| POST | `/teams/:teamId/squads/:squadId/agents` | `{agent_id,position?}` → 201 assignment |
| DELETE | `/teams/:teamId/squads/:squadId/agents/:agentId` | Remove assignment; 204 |

Squad record: `{id,team_id,name,goal,created_at}`. Goal max 2000 characters. One agent can be assigned to multiple squads but receives that squad's context per run. Position determines execution order; assign distinct positions for a predictable order. Initial runs require one to three agents.

## Context and handoffs

| Method | Path | JSON body / result |
| --- | --- | --- |
| GET | `/teams/:teamId/squads/:squadId/context` | Latest 50 entries by default, chronological; query `limit=1..100`, optional `before=<ISO timestamp>` |
| POST | `/teams/:teamId/squads/:squadId/context` | `{content}` → 201 note; max 16000 characters |
| POST | `/teams/:teamId/squads/:squadId/handoffs` | `{target_squad_id,content}` → 201 handoff in target context |

Entry record: `{id,team_id,squad_id,kind,content,source_squad_id,run_id,created_by,created_at}`. Kinds: `note`, `result`, `handoff`. Render content as plain text or sanitized Markdown. Handoffs copy only the provided content with source provenance, not the source squad's whole context. Target must be a different squad in the same team. Older content can be fetched using `before`; this timestamp-only initial cursor can omit entries sharing the boundary timestamp, so don't use it for archival exports.

## Agent runs

| Method | Path | JSON body / result |
| --- | --- | --- |
| POST | `/teams/:teamId/squads/:squadId/runs` | `{goal}` → 202 queued run; goal max 2000 characters |
| GET | `/teams/:teamId/squads/:squadId/runs` | Latest 30 runs, newest first |
| GET | `/teams/:teamId/runs/:runId` | Run plus chronological `entries` generated by that run |
| POST | `/teams/:teamId/runs/:runId/recover` | `{confirm_interrupted:true}` → mark an interrupted persisted run failed; rejects jobs still scheduled in this backend |

Run: `{id,team_id,squad_id,created_by,goal,status,error,created_at,updated_at}`. Statuses: `queued` → `running` → `completed` or `failed`. Agent output becomes a `result` context entry. Tool-generated handoffs are also linked to the source run. Show queue/running/failure states and disable repeat submission while the squad has an active run. Duplicate active runs receive 409. Model queue capacity is eight, globally serialized in one backend process.

The backend supplies team/squad IDs and author fields. Do not submit these fields in bodies. No shell or arbitrary external web tools are exposed. Tools are bounded to listing same-team squads and publishing a finding to a verified same-team target.

## Event-planning demo (squads + missions)

| Method | Path | JSON body / result |
| --- | --- | --- |
| POST | `/teams/:teamId/event-squads` | No body → 201 `{agents, venue_squad_id, promo_squad_id, logistics_squad_id}`. Creates Venue Squad (Event Manager, Scout, Budget Keeper), Promo Squad (Copywriter, Art Director), Logistics Squad (Scheduler, Event Manager). Call once per team; calling again creates duplicates. |
| POST | `/teams/:teamId/missions` | `{brief, venue_squad_id, promo_squad_id, logistics_squad_id}` → 202 `{status:"queued", brief_entry_id, steps}`. Brief max 1500 characters. 409 if any of the three squads has an active run. |

A mission posts the brief as a `note` in the Venue Squad, then runs the squads one after another, Venue → Promo → Logistics, with every assigned agent in each. Each step creates a normal run, so track progress with `GET /teams/:teamId/squads/:squadId/runs` (or Realtime on `runs`) for each squad. Later steps' runs appear only once earlier steps complete. A failed step stops the mission.

Within a squad, agents run in position order and each sees teammates' earlier results. Squads share only through `handoff` entries. Agents create them with `share_finding`; if a step completes without handing off to the next squad, the backend forwards its results as a handoff whose content starts `[automatic handoff: <squad> results]`. Show that label so judges can tell agent handoffs from automatic ones.

Venue Squad agents also get `find_venues` (OpenStreetMap, no key) and `read_page` (public HTTPS page text, 3000 characters). The final package is the Logistics Squad's `result` entries. Emails and invites are drafts marked for player approval; nothing is sent. The Art Director's flyer is model-written HTML: render it only in `<iframe sandbox srcdoc=...>` without `allow-scripts`, never with innerHTML. Mission steps have a 420-second elapsed guard each; expect several minutes on CPU.

## Live updates

Frontend can use Supabase Postgres Changes with its signed-in session. Subscribe to INSERT/UPDATE on `runs`, `context_entries`, `agents`, `squads`, and `squad_agents` using a `team_id=eq.<teamId>` filter and refetch relevant API data after events. Database RLS determines visible rows. Do not use unauthenticated public broadcast rooms for private team content. For membership/team changes, refetch `/teams` and the member list.

Avoid DELETE subscriptions: Supabase has different RLS behavior for deleted records. Refetch after explicit removal or on reconnect. Polling run detail every 2–3 seconds is a simple fallback; stop on completion/failure. Hosted INSERT delivery to an authorized teammate and outsider non-delivery have passed the live smoke check.

Subscription readiness matters: `SUBSCRIBED` alone can precede database replication readiness. With the current Supabase JS SDK, use `.channel(name, {config: {postgres_changes_options: {wait: true, timeout: 15000}}})` and allow at least 25 seconds for setup. Alternatively wait for the system message with `extension === 'postgres_changes'` and `status === 'ok'`. Then refetch the latest API state to cover any events missed during connection/reconnection. See [Supabase's timing guidance](https://supabase.com/kb/troubleshooting/realtime-postgres-changes-troubleshooting#step-6-writing-right-after-subscribed).

## Local setup and readiness

Allowed browser origins come from comma-separated exact `FRONTEND_ORIGIN` values. Backend binds `127.0.0.1` by default. To use another computer on the same trusted network, explicitly configure `HOST=0.0.0.0` and the actual frontend origin; keep Ollama itself on loopback. A hosted frontend cannot reach another person's localhost; coordinate the demo network before integration.

`GET /health` reports process liveness; `GET /ready` checks local model availability and schema access, returning 200 or 503 with component readiness. It does not run inference or expose credentials. SQL migration must be applied before database-backed endpoints work. See `backend/migrations/README.md`.

The execution queue is in memory. A backend restart loses queued jobs; persisted active rows do not automatically resume. After confirming that a run was interrupted, use `/recover` to release its squad before retrying. Never use recovery against work executing in a different backend instance. Do not run multiple API replicas for this demo. Live cancellation and a durable worker are not implemented.

Each agent gets up to three model rounds and each round permits up to two tool calls. The run has a 180-second elapsed guard and each in-flight model request has a 90-second timeout. A late request is awaited rather than abandoned; therefore a failed run can take up to roughly 270 seconds to report failure. Late output is not persisted as a successful result.
