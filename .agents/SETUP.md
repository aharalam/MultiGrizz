# Agent-run first-use setup

Run this automatically when a coding agent first opens this checkout, before substantial project work. Repeat the quick checks in a later session; install only what is missing. Set up **the active harness only**. Do not infer the active harness from which executables happen to be installed, and do not require the human to run a bootstrap command.

1. **Check the checkout.** Confirm that `AGENTS.md`, `CLAUDE.md`, the three `.hackathon/` state files, and the project-local skill entry points for `hackathon-competition`, `grill-me`, `grilling`, `ponytail`, `impeccable`, and `web-design-guidelines` exist. Check the active agent's skill inventory where available. These skills are committed; do not reinstall them just because this is a new machine. If files are missing, report the incomplete checkout and repair it from the repository's own Git history when possible.
2. **Check Superpowers.** Look for active Superpowers skills and an enabled Superpowers plugin in the active harness. For Codex, `codex plugin list --json` can help; for Claude Code, use `claude plugin list --json` when available. A sandbox-denied profile read or an unexpectedly empty CLI list is **inconclusive**, especially when the active agent already exposes Superpowers skills. Recheck with the appropriate profile access before attempting an install. If the plugin is present but disabled, enable that existing installation through the harness's plugin controls and verify; do not reinstall it.
3. **Install Superpowers if genuinely missing.** Read the current installation section of [obra/superpowers](https://github.com/obra/superpowers) before installing. Use only its official harness marketplace. In Codex, try the supported CLI command `codex plugin add superpowers@openai-curated-remote --json`; if that catalog or CLI route is unavailable, direct the human to **Plugins → Superpowers → +** in the app or `/plugins` in Codex CLI. In Claude Code, try `claude plugin install superpowers@claude-plugins-official`; if interactive installation is required, give the human that exact slash command. Do not substitute a copied skill or a fork. Request normal tool permission for profile or network access if the environment requires it; do not call a denied or unreadable profile "not installed."
4. **Verify after installation.** Check the plugin is enabled and its skills are discoverable in a fresh agent session. Tell the human to start a new chat/session if the current one cannot load newly installed plugins. Never report success based solely on an install command's exit code.
5. **Check Impeccable.** Confirm the project-local skill exists. Its committed launcher fetches a version-pinned binary from the original upstream release when needed and verifies its hash. In Claude Code, the hook manifest is the ignored `.claude/settings.local.json`, so a new clone will lack it. Check Impeccable's hook status; unless the user has explicitly disabled the hook, run the bundled `impeccable hooks on` command from `.claude/skills/impeccable/scripts/` to create or repair the local manifest, then verify it exists. On Windows use `impeccable.cmd`; on macOS/Linux use `impeccable`. In Codex, check the committed `.codex/hooks.json`. If hook approval is pending **or you cannot verify approval**, send this direct prompt: “Please open `/hooks` in Codex, review and approve this repository's Impeccable hook, then tell me when it is approved.” Keep it pending until the human responds; verify before claiming the hook is active. Do not bypass the trust prompt. Run Impeccable's `init` when a real product has been selected, not during blank-template setup.
6. **Prompt for every remaining manual step.** If a plugin UI action, login, permission, hook approval, or new session is required, ask the human directly in the conversation with the exact action and why it is needed. Use the harness's user-input prompt when available. Do not bury actions in a status paragraph or README, silently assume completion, or repeat a prompt already completed and verified. Continue independent work while a reply is pending; wait for the reply before claiming dependent setup complete.
7. **Finish with a short status.** State what was already available, what you installed and verified, and what is still awaiting the human. Then continue with the user's actual hackathon task. Do not make the human repeat checks or fill out setup forms.

React Best Practices stays uninstalled until the actual project uses React or Next.js. If the active harness cannot execute a step, continue independent work and give the human only the blocked action with its reason.
